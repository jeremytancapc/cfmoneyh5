# AXS appointment status sync — implementation plan

Status (2026-10-28):
- **AirConnect side:** built, in TCaken/t3gallery#312.
- **H5 side:** built on branch `feature/axs-status-sync`, not committed yet.

See "As built" at the end for where the code differs from this plan. Covers cfmoneyh5
(this repo) and AirConnect (t3gallery). The 60-day reapply rule that came up in the
same session is a separate piece of work:
`t3gallery/docs/reapply-rule-60-day-plan.md`.

## Goal

The AXS app shows the customer where their appointment stands. After a cancel or a
miss, they rebook from the same link.

## Decisions

| Topic | Decision |
|---|---|
| Who talks to AXS | Only cfmoneyh5. AirConnect is not public-facing and never calls AXS. |
| Source of truth | AirConnect. Agents manage appointments there. |
| Transport | AirConnect pushes to cfmoneyh5 when an appointment changes. No polling, no backup check. |
| Failures | Logged, then dropped. No retry, no resend queue. |
| Scope | AXS bookings only, from release onwards. No backfill. |
| Statuses sent to AXS | `booked`, `rescheduled`, `cancelled`, `missed`. No `completed`. AXS already accepts these. |
| Timing | Sent as it happens. No hold on cancellations. |
| Rebooking | The same booking link. It works again only after a cancel or a miss. |
| No AirConnect appointment ever made | Leave it. AXS keeps showing `booked`. |
| Lead source | New AXS leads in AirConnect get `source = 'AXS'`. Existing leads keep their source. No AXS-specific reapply rule. |
| Respond.io | Add `AXS` to Respond.io's `lead_source` list before release. |
| AXS reloan rejections | Note it on the AirConnect borrower so the reloan team sees it. |

**Accepted gaps:**
- Cancels done through the Respond.io bot are not pushed.
- Borrower (reloan) appointments are not pushed. AXS hard-rejects existing borrowers,
  so this only matters if a customer becomes a borrower between submit and booking.
- A failed push is lost. The customer simply doesn't see that update.

## Event mapping

| AirConnect function | Event | cfmoneyh5 appointment row | AXS gets | Link reusable |
|---|---|---|---|---|
| `createAppointment` | `created` | `confirmed`, agent's slot (reopened if it was cancelled or missed) | `booked` + slot | no |
| `moveAppointmentToTimeslot` | `moved` | `confirmed`, new slot | `rescheduled` + slot | no |
| `cancelAppointment` | `cancelled` | `cancelled` | `cancelled` + link | yes |
| `updateAppointmentStatus` → `cancelled` | `cancelled` | `cancelled` | `cancelled` + link | yes |
| `updateAppointmentStatus` → `missed` | `missed` | `missed` | `missed` + link | yes |
| branch-sheet import (`status-update/route.ts:1124`) → `missed` | `missed` | `missed` | `missed` + link | yes |
| `updateAppointmentStatus` → `done` | `done` | `completed` | nothing | no |

A push is only sent for appointments created on or after the customer's latest AXS
booking. An older, unrelated appointment on a reused lead never triggers one.

Nothing sent to AXS carries a name, phone or NRIC. It carries only `reference_id`, the
status, the date, the time, `booking_url` and `metadata.booking_id`, the same shape as
today's booking webhook.

## AirConnect (t3gallery)

### A1. Migration `drizzle/0015_h5_links.sql`

Same ownership pattern as `t3gallery_credit_limits`.

```sql
CREATE TABLE IF NOT EXISTS "t3gallery_h5_links" (
  "id" integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  "h5_lead_id" uuid NOT NULL,                -- cfmoneyh5 leads.id
  "channel" varchar(20) NOT NULL,            -- 'axs' (only value for now)
  "lead_id" integer REFERENCES "t3gallery_leads" ("id") ON DELETE CASCADE,
  "borrower_id" integer REFERENCES "t3gallery_borrowers" ("id") ON DELETE CASCADE,
  "booked_at" timestamp with time zone NOT NULL,   -- latest AXS booking
  "created_at" timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT "h5_links_one_owner" CHECK (("lead_id" IS NOT NULL) <> ("borrower_id" IS NOT NULL))
);
CREATE UNIQUE INDEX IF NOT EXISTS "h5_links_h5_lead_idx" ON "t3gallery_h5_links" ("h5_lead_id");
CREATE INDEX IF NOT EXISTS "h5_links_lead_idx" ON "t3gallery_h5_links" ("lead_id");
```

- Add the `createTable` entry in `src/server/db/schema.ts`.
- Apply to dev first, then prod.

### A2. New AXS-only booking endpoint `POST /api/appointments/axs`

The normal H5, AIP and AXS bookings all post to `/api/appointments/cfh5` today,
through one shared env var. AXS gets its own route so none of this can affect the
H5 or AIP bookings. **The `cfh5` route stays unchanged.**

- **Route:** `src/app/api/appointments/axs/route.ts`. It has the same `ASCEND_API_KEY`
  check and field validation as `cfh5/route.ts`, moved into a small shared helper
  that both routes call.
- **Required fields:** `leadId` must be a UUID, or the route returns 400. An AXS
  booking can't arrive without its link.
- **Lead flow:** it calls the same `processAppointmentReminderWithLeadProcessing` →
  `processAscendLeadForAppointment` with `ascend_status = 'submitted_from_h5'`,
  passing `{ h5LeadId, channel: 'axs' }` and `source: 'AXS'`. It stays on the
  shared lead logic, so the reapply rule applies to AXS like any other channel.
- **New-lead branch:** `createLead({ source: 'AXS', ... })` instead of `'SEO'`.
- **Duplicate-lead branch:** source unchanged.
- **Reloan branch:** link to the borrower (it gets no pushes, but stays traceable).
- Add `saveH5Link(owner, link)` and call it next to each `saveCreditLimit(...)`.
  - Upsert on `h5_lead_id`, with `booked_at = now()`.
  - A failure is logged and never fails the booking.

### A3. Push helper `src/app/_actions/h5AppointmentPush.ts`

`notifyH5AppointmentChange(appointmentId, event)`:
- Load the appointment and its lead's `t3gallery_h5_links` row (`channel = 'axs'`).
  Return immediately if there's no link, or if `appointment.created_at < booked_at`.
  That's the common case, and it costs one indexed lookup.
- POST `{ h5LeadId, event, appointmentId, startDatetime }` to cfmoneyh5
  `/api/airconnect/appointment-event` with `x-api-key: H5_EVENT_WEBHOOK_KEY`.
- Await with a 5s timeout. On any error, write to `t3gallery_logs`
  (`entity_type: 'h5_push'`) and return. **It never throws into the caller**, so an
  agent's action never fails because cfmoneyh5 is down.

Call it, after the DB write succeeds, from:
- `createAppointment` (`appointmentAction.ts:181`)
- `moveAppointmentToTimeslot` (`appointmentAction.ts:1115`): send the new
  appointment's ID
- `cancelAppointment` (`appointmentAction.ts:406`)
- `updateAppointmentStatus` (`appointmentAction.ts:513`), for `cancelled`, `missed`
  and `done`
- the branch-sheet import's lead path (`status-update/route.ts:1124`)

Tests (vitest): no link → no call; appointment older than `booked_at` → no call; a
fetch error is logged and swallowed; the event name for each caller.

### A4. Borrower note endpoint (AXS reloan rejections)

`POST /api/borrowers/reapply-note`, authenticated with `ASCEND_API_KEY`, takes
`{ phoneNumber, idNumber?, source: 'AXS' }`. It finds the borrower and adds a note,
"Reapplied via AXS - <SGT timestamp>", plus a `t3gallery_logs` entry. It returns
`{ found }` and nothing else.

## cfmoneyh5 (this repo)

### C0. Point AXS bookings at the new endpoint

- `notifyAirConnect` in `app/api/axs/book/route.ts` reads a new env var,
  `AIRCONNECT_AXS_APPOINTMENTS_URL`, set to A2's URL, instead of the shared
  `AIRCONNECT_APPOINTMENTS_URL`.
- `apply/book` and `aip/book` don't change.
- If the new var is missing, the route logs it and skips the AirConnect call, the
  same way it handles a missing URL today. It does not fall back to the shared
  URL, which would silently recreate unlinked AXS leads.

### C1. Migration `supabase/migrations/2026MMDD000001_axs_status_sync.sql`

- `alter type public.appointment_status add value if not exists 'missed';`
- `appointments` gets:
  - `airconnect_appointment_id integer`
  - `axs_notified_status text`
  - `axs_notified_at timestamptz`
- `leads` gets `axs_booking_token text`, written in `/api/axs/submit`, so every
  status update sends the exact link the customer already has. Leads from before this
  migration fall back to re-minting with `createAxsToken`.

### C2. Shared AXS webhook `lib/axs-webhook.ts`

- Move `notifyBookingWebhook` out of `app/api/axs/book/route.ts` and give it a
  `status` parameter. The book route keeps sending `"booked"`.
- Return `ok`, so the caller records `axs_notified_*` only on success.

### C3. Booking lock

`/api/axs/book` currently blocks a second booking only while a row is `confirmed`.
Change that to `status in ('confirmed', 'completed')`. Otherwise a `done` from
AirConnect would reopen the link.

### C4. Event receiver `app/api/airconnect/appointment-event/route.ts`

- **Auth:** check `x-api-key` against `H5_EVENT_WEBHOOK_KEY`.
- **Lookup:** load the lead by `h5LeadId`, then its latest appointment row. Reject
  unless `auth_method = 'axs'`.
- **Decide:** a pure function, `decideAxsEvent(localRow, event)` in
  `lib/axs-status-sync.ts`, unit-tested, applies the event-mapping table above:
  - `created` on a cancelled or missed row inserts a new `confirmed` row.
  - `created` or `moved` on a `confirmed` row updates its slot.
- **Send:** call C2 with `booking_url` for `cancelled` and `missed`, and with the slot
  for `booked` and `rescheduled`.
- **Skip:** don't send when (status, date, time) equals what `axs_notified_*` already
  holds. That makes a repeated push harmless.
- **Logging:** log everything through `logExternalApi`.
- **Response:** return 200 even when the AXS call fails. AirConnect doesn't retry.
- **Kill switch:** `AXS_STATUS_SYNC_ENABLED=true` must be set, or the route logs the
  event and does nothing.

### C5. Reloan rejection note

In `/api/axs/submit`, when eligibility comes back `RELOAN`, call A4 inside `after()`
from `next/server`. AXS gets its response without waiting for the note, and any
failure is logged. Read the Next 16 `after` doc in `node_modules/next/dist/docs/`
before using it.

## Rollout

1. **Release blocker:** add `AXS` to Respond.io's `lead_source` list.
2. A1–A4 on AirConnect dev. C0–C5 on cfmoneyh5 `stg` with the kill switch off.
   Set `AIRCONNECT_AXS_APPOINTMENTS_URL` in each cfmoneyh5 environment before
   deploying C0.
3. Point AirConnect dev at cfmoneyh5 stg. Book a test AXS lead, then in AirConnect
   dev create, move, cancel, mark missed and mark done. Check `api_logs` and
   `t3gallery_logs` after each.
4. Turn the kill switch on in UAT against the AXS UAT webhook. Run the same
   scenarios with AXS.
5. Production order:
   1. AirConnect prod migration.
   2. Deploy AirConnect, so the new endpoint is live.
   3. Set the env var and deploy cfmoneyh5.
   4. Enable the sync. Read
   `api_logs` daily for the first week, since failures are not retried.

## As built (2026-10-28)

### Where the code differs from the plan

- **`cfh5` route is untouched.** The API key and field checks are repeated in
  `/api/appointments/axs` instead of moved into a shared helper, so the normal H5
  and AIP bookings can't be affected.
- **AirConnect pushes after the response.** Pushes run in `after()` rather than
  being awaited with a 5s timeout, so an agent's action is never delayed. The
  push itself has a 5s timeout.
- **More bookings push than planned.** The push lives inside `createAppointment`,
  so appointments created through the Respond.io bot or the branch-sheet import
  also push `created`.
- **The AXS route defaults `app` to `axs`, never `cfh5`.** `cfh5` skips the
  Ascend reloan check.
- **The booking lock is shared.** "Confirmed or completed" lives in
  `BOOKING_LOCK_STATUSES` (`lib/axs-status-sync.ts`), used by both
  `/api/axs/book` and the `/axs/book` page.
- **Reapply note masking.** The note call's identifiers are masked to the last 4
  characters in `api_logs`.
- **Old leads get a fresh link.** Leads with no stored `axs_booking_token` get a
  newly minted, valid link. It uses the approved amount, falling back to the
  amount AXS asked for.

### Environment variables

| Where | Variable | Value |
|---|---|---|
| AirConnect | `H5_APPOINTMENT_EVENT_URL` | `<H5 base>/api/airconnect/appointment-event` |
| AirConnect | `H5_EVENT_WEBHOOK_KEY` | shared secret (same value as below) |
| H5 | `H5_EVENT_WEBHOOK_KEY` | same shared secret |
| H5 | `AIRCONNECT_AXS_APPOINTMENTS_URL` | `<AirConnect base>/api/appointments/axs` |
| H5 | `AIRCONNECT_REAPPLY_NOTE_URL` | `<AirConnect base>/api/borrowers/reapply-note` |
| H5 | `AXS_STATUS_SYNC_ENABLED` | `true` to act on events. Anything else: log only |

`AIRCONNECT_API_KEY` (H5) is reused for both new AirConnect calls. AirConnect
checks it against its existing `ASCEND_API_KEY`.

### Deploy order

Each step is safe on its own:
1. **Migrations:**
   - AirConnect `drizzle/0015_h5_links.sql` (applied on dev).
   - H5 `supabase/migrations/20261028000001_axs_status_sync.sql` (not applied
     anywhere yet).
2. **Deploy AirConnect** with its env vars set.
3. **Deploy the H5** with `AIRCONNECT_AXS_APPOINTMENTS_URL` set, and
   `AXS_STATUS_SYNC_ENABLED` unset.
4. **Turn the sync on.** Test in UAT, then set `AXS_STATUS_SYNC_ENABLED=true`.

**Warning:** if the H5 is deployed without `AIRCONNECT_AXS_APPOINTMENTS_URL`,
AXS bookings stop reaching AirConnect at all. This is deliberate, so it can't
silently fall back to unlinked leads. Set the variable before deploying.
